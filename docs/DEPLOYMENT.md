# Deploying Merkel Engineering to Vercel

A step-by-step guide for the workflow: **replace the images → fork to your GitHub →
deploy on Vercel → switch the backend on**.

Everything here fits inside free tiers (Vercel Hobby, Upstash Redis, Resend).

---

## How it fits together

| Piece | Where it runs |
| ----- | ------------- |
| Pages, CSS, JS, images | Vercel's CDN (static, generated by `npm run build`) |
| `/api/*` (projects, careers, contact, chat) | One Vercel serverless function (`api/[...path].js`) |
| Enquiries + chat transcripts | Redis (Vercel KV / Upstash) |
| Inbox notifications | Resend email and/or a webhook |

**One thing to know up front:** Vercel is serverless, so the filesystem is not
writable and nothing survives between requests. Locally the app writes enquiries and
chats to `./data`; in production it needs Redis. That is what Step 4 sets up. Until
you complete Step 4, the site works and email still sends, but transcripts are not
durably stored.

## Step 1: Replace the placeholder images

All current artwork is generated blueprint-style placeholder SVG. Drop your real
images into `public/assets/` and point these fields at them.

**Page-level artwork.** Edit `src/data/images.json`:

| Key | Appears on | Suggested size |
| --- | ---------- | -------------- |
| `heroSlides[]` | Home hero slideshow (add or remove entries; the dots follow automatically) | 1920 × 900, landscape |
| `servicesMedia` | Home, beside the Services heading | 1200 × 750 (16:10) |
| `projectsHeader` | `/projects` header band | 1920 × 800 |
| `careersHeader` | `/careers` header band | 1920 × 800 |
| `contactHeader` | `/contact` header band | 1920 × 800 |
| `ctaBand` | "Bring us the hard part" band on home and project pages | 1920 × 800 |

**Per-project images.** Edit the `image` field in `src/data/projects.json` (one per
project; also used as the card thumbnail and the detail-page figure). Suggested size
1200 × 820 (roughly 3:2).

**CEO portrait.** Edit the `image` field in `src/data/leadership.json`. Suggested
size 760 × 950 (4:5 portrait).

**Logo.** Already your artwork, in `public/assets/brand/`. `merkel-wordmark.png` is
the transparent version used in the nav and footer.

Notes:

- Any web format works (`.webp`, `.jpg`, `.png`, `.svg`). WebP or optimised JPEG is
  best for photographs; keep each file under roughly 400 KB.
- Header and hero images sit behind a dark overlay, so pick images that stay readable
  when darkened. Busy, high-contrast photos work well.
- `public/js/main.js` contains a small `FALLBACK_PROJECTS` list used only if the API
  is unreachable. If you rename project image files, update those paths too (optional).
- After editing, run `npm run build` to regenerate the pages, or just let Vercel do it
  on deploy.

## Step 2: Fork to your GitHub

1. Open the repository on GitHub and click **Fork** (top right).
2. Choose your account as the owner and create the fork.
3. Clone it and add your images:

   ```bash
   git clone https://github.com/<your-username>/<your-repo>.git
   cd <your-repo>
   npm install
   # ... replace images and edit src/data/images.json ...
   npm run build && npm start     # check http://localhost:3000
   git add -A && git commit -m "Add real project imagery" && git push
   ```

---

## Step 3: Deploy to Vercel

1. Go to <https://vercel.com> and sign in with GitHub.
2. **Add New → Project**, then import your forked repository.
3. Leave the build settings as they are. `vercel.json` already sets:
   - Build command: `npm run build`
   - Output directory: `public`
   - Clean URLs, plus the `/projects/:id` rewrite
4. Click **Deploy**.

The site will be live in about a minute. The pages, images and the API all work at
this point; the chat replies and the contact form accept submissions. Storage and
email come next.

---

## Step 4: Add free storage (Vercel KV / Upstash Redis)

This is what makes enquiries and chat transcripts persist.

1. In your Vercel project, open the **Storage** tab.
2. Create a **Redis** store (listed as Vercel KV, or Upstash Redis via the
   Marketplace). Pick the free plan and a region near your users.
3. **Connect** the store to your project, for all environments
   (Production, Preview, Development).
4. Vercel injects the credentials as environment variables. Open
   **Settings → Environment Variables** and confirm you have one of these pairs:

   | Pair | Provided by |
   | ---- | ----------- |
   | `KV_REST_API_URL` + `KV_REST_API_TOKEN` | Vercel KV |
   | `UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN` | Upstash integration |

   The app accepts **either pair**, so no code change is needed. If your provider uses
   different names, just add one of the supported pairs with the same values.

5. Redeploy (**Deployments → ⋯ → Redeploy**) so the function picks up the variables.

You will see `[merkel] storage: Redis (Vercel KV / Upstash)` in the function logs on
the next request. Enquiries are stored in the list `merkel:submissions`, and each
conversation in `merkel:chat:<sessionId>` (trimmed to the last 200 messages and
expiring after 90 days).

---

## Step 5: Route enquiries and chat to your inbox (email)

1. Sign up at <https://resend.com> (free tier: 3,000 emails a month).
2. **API Keys → Create API Key**, and copy it.
3. In Vercel, **Settings → Environment Variables**, add:

   | Name | Value |
   | ---- | ----- |
   | `RESEND_API_KEY` | the key you just copied |
   | `CONTACT_NOTIFY_EMAIL` | where you want messages to land (comma-separate for several) |
   | `NOTIFY_FROM` | `Merkel Website <onboarding@resend.dev>` to start |

4. Redeploy.

For production, verify your own domain in Resend (**Domains → Add Domain**, then add
the DNS records) and change `NOTIFY_FROM` to something like
`Merkel Website <studio@yourdomain.com>`. Mail from a verified domain is far less
likely to land in spam than the shared testing sender.

You will now get an email for every contact-form enquiry and every live-chat message.
To stop the chat emails while keeping enquiry emails, set `CHAT_NOTIFY=off`.

---

## Step 6: Send to a desk provider (optional)

Set `NOTIFY_WEBHOOK_URL` to any endpoint that accepts a JSON `POST`. The payload is:

```json
{
  "subject": "New enquiry from Ines Hart",
  "text": "Name: ...\nEmail: ...\n\nmessage body",
  "content": "same as text",
  "data": { "id": "...", "name": "...", "email": "...", "message": "..." }
}
```

- **Slack:** create an Incoming Webhook and paste the URL. Slack renders the `text` field.
- **Discord:** use a channel webhook URL. Discord renders the `content` field.
- **Zapier / Make / a help desk:** point it at a catch hook and map `data` to a ticket.

Email and webhook are independent: configure either, or both.

## Step 7: Test it

On your live URL:

1. `/` loads, the hero slideshow rotates through your images.
2. `/projects` lists your projects; click one for the full page.
3. `/careers` lists open roles; `/contact` shows the form.
4. Submit the contact form → you get the success message **and** an email/webhook.
5. Open the chat bubble, send a message → you get a reply, **and** a notification.
6. Reload the page and reopen the chat; the conversation is still there
   (this is what confirms Step 4 is working).
7. Visit a nonsense URL such as `/nope` and confirm the styled 404 page.

Quick API check from a terminal:

```bash
curl -s https://<your-app>.vercel.app/api/health
curl -s https://<your-app>.vercel.app/api/projects | head -c 200
```

## Reading what has been collected

The data lives in Redis. The easiest way to read it is the **Data Browser** in the
Vercel Storage tab or the Upstash console:

- `merkel:submissions` is a list of contact enquiries (newest first)
- `merkel:chat:sessions` is a set of every chat session id
- `merkel:chat:<sessionId>` is one conversation, oldest first

Because every enquiry and chat message is also emailed to you, your inbox is the
practical day-to-day record; Redis is the durable archive and what powers chat history
for the visitor.

## Local development

```bash
npm install
cp .env.example .env      # optional
npm run build             # generate public/*.html
npm start                 # http://localhost:3000
npm run dev               # build + auto-restart
```

With no environment variables set, the app writes to `./data/` (git-ignored) and
notifications are skipped, so you can develop entirely offline. To test notifications
locally, set `NOTIFY_WEBHOOK_URL` to a <https://webhook.site> URL.

---

## Environment variable reference

| Variable | Required | Purpose |
| -------- | -------- | ------- |
| `KV_REST_API_URL` / `KV_REST_API_TOKEN` | for persistence | Vercel KV credentials |
| `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` | alternative | Upstash credentials |
| `RESEND_API_KEY` | for email | Resend API key |
| `CONTACT_NOTIFY_EMAIL` | for email | Destination inbox (comma-separated for several) |
| `NOTIFY_FROM` | no | Sender identity; must be verified in Resend |
| `NOTIFY_WEBHOOK_URL` | no | Slack / Discord / desk webhook |
| `CHAT_NOTIFY` | no | `off` to stop chat notifications (default `on`) |
| `DATA_DIR` | no | Override the filesystem storage path |
| `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX` | no | API rate limiting (defaults 60000 / 30) |
| `PORT` | no | Local port (default 3000) |

## Troubleshooting

**Chat history disappears on reload (in production).** Redis is not connected. Recheck
Step 4, especially that the variables exist in the **Production** environment and that
you redeployed afterwards.

**No emails arriving.** Check the function logs (**Deployments → your deployment →
Functions**) for `notify email failed`. The usual causes are a missing
`CONTACT_NOTIFY_EMAIL`, or a `NOTIFY_FROM` address on a domain you have not verified
in Resend.

**The contact form still succeeds when email fails.** That is deliberate: persistence
and notification are best effort and never block a visitor's submission. Check the logs
to see what failed.

**A 404 on `/projects/something`.** The `/projects/:id` rewrite in `vercel.json` sends
these to `project.html`, which loads the project by id. Confirm the id matches an entry
in `src/data/projects.json`.

**Rate limiting feels inconsistent.** The limiter is in-memory, so on serverless each
instance counts separately. It is a speed bump, not a hard quota. Move it to Redis if
you need strict limits.
