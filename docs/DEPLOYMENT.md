# Deploying Merkel Engineering to Vercel

A step-by-step guide for the workflow: replace the images, fork to your GitHub,
deploy on Vercel, then switch the backend on.

Everything here fits inside free tiers (Vercel Hobby, Neon, Resend).

---

## How it fits together

| Piece | Where it runs |
| ----- | ------------- |
| Pages, CSS, JS, images | Vercel's CDN (static, generated by `npm run build`) |
| `/api/*` (projects, careers, contact, chat, inbound mail) | One Vercel serverless function (`api/[...path].js`) |
| Enquiries, chat transcripts, inbound mail | Neon (serverless Postgres) |
| Outgoing notifications | Resend email, optionally a webhook |
| Incoming mail to your domain | Resend inbound, forwarded to a real inbox |

**One thing to know up front:** Vercel is serverless, so the filesystem is not
writable and nothing survives between requests. Locally the app writes to `./data`;
in production it needs a database. Step 4 sets that up.

The storage backend is chosen automatically at runtime:

1. **Neon / Postgres**, when `DATABASE_URL` is set
2. **Supabase**, when `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are set
3. **Redis**, when Vercel KV or Upstash credentials are set
4. **Local files**, otherwise (development)

## Step 1: Replace the placeholder images

All current artwork is generated blueprint-style placeholder SVG. Drop your real
images into `public/assets/` and point these fields at them.

**Page-level artwork.** Edit `src/data/images.json`:

| Key | Appears on | Suggested size |
| --- | ---------- | -------------- |
| `heroSlides[]` | Home hero slideshow (add or remove entries; the dots follow automatically) | 1920 x 900 |
| `servicesMedia` | Home, beside the Services heading | 1200 x 750 |
| `projectsHeader` | `/projects` header band | 1920 x 800 |
| `careersHeader` | `/careers` header band | 1920 x 800 |
| `contactHeader` | `/contact` header band | 1920 x 800 |
| `ctaBand` | "Bring us the hard part" band on home and project pages | 1920 x 800 |

**Per-project images.** Edit the `image` field in `src/data/projects.json` (one per
project; used for the card thumbnail and the detail-page figure). Suggested size
1200 x 820.

**CEO portrait.** Edit the `image` field in `src/data/leadership.json`. Suggested
size 760 x 950 (4:5 portrait).

**Logo.** Already your artwork, in `public/assets/brand/`.

Notes:

- Any web format works (`.webp`, `.jpg`, `.png`, `.svg`). Keep files under ~400 KB.
- Header and hero images sit behind a dark overlay, so pick images that stay readable
  when darkened.
- `public/js/main.js` has a small `FALLBACK_PROJECTS` list used only if the API is
  unreachable. Update those paths too if you rename project image files (optional).
- Run `npm run build` after editing, or let Vercel do it on deploy.

## Step 2: Fork to your GitHub

1. Open the repository on GitHub and click **Fork**.
2. Clone it, add your images, and check it locally:

   ```bash
   git clone https://github.com/<your-username>/<your-repo>.git
   cd <your-repo>
   npm install
   # replace images, edit src/data/images.json
   npm run build && npm start        # http://localhost:3000
   git add -A && git commit -m "Add real imagery" && git push
   ```

---

## Step 3: Deploy to Vercel

1. Go to <https://vercel.com> and sign in with GitHub.
2. **Add New, then Project**, and import your fork.
3. Leave the build settings alone. `vercel.json` already sets the build command,
   the `public` output directory, clean URLs and the `/projects/:id` rewrite.
4. Click **Deploy**.

The site is live in about a minute. Pages, images and the API work; storage and email
come next.

---

## Step 4: Add the database (Neon)

1. In your Vercel project open the **Storage** tab, choose **Neon** from the
   Marketplace, pick the free plan and **Connect** it to the project (all
   environments). Vercel injects `DATABASE_URL` automatically.

   Already created the database at <https://neon.tech> instead? Copy the pooled
   connection string from the Neon Console and add it as `DATABASE_URL` under
   **Settings, Environment Variables**.

2. Create the tables. In the **Neon Console**, open **SQL Editor** and run the
   contents of [`db/schema.sql`](../db/schema.sql). From a terminal instead:

   ```bash
   psql "$DATABASE_URL" -f db/schema.sql
   ```

   That creates `enquiries`, `chat_messages` and `inbound_emails` with indexes.

3. **Redeploy** so the function picks the variable up.

The function logs `[merkel] storage: Neon (Postgres)` on the next request.

**Notes.**

- The app uses Neon's HTTP driver, which issues one request per query. That
  avoids the connection-pool exhaustion TCP drivers hit on serverless, so the
  pooled connection string is the right one to use.
- Every query is parameterised, so values are never concatenated into SQL.
- `DATABASE_URL` is a credential. Keep it server side; never expose it to the
  browser or put it behind a `VITE_` prefix.
- Other accepted names: `POSTGRES_URL`, `NEON_DATABASE_URL`,
  `DATABASE_URL_UNPOOLED`, `POSTGRES_URL_NON_POOLING`.

### Using Supabase instead

1. Create the tables: in the Supabase dashboard open **SQL Editor, New query**,
   paste [`db/schema.supabase.sql`](../db/schema.supabase.sql) and **Run**. It is the
   same three tables as Neon, plus row level security.
2. In Supabase open **Project Settings, API** and copy the **Project URL** and the
   **`service_role`** key.
3. In Vercel add `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, then **Redeploy**.
   Vercel's Supabase integration usually adds both for you; check they are present.
   `VITE_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_URL` also work as the URL.

The function then logs `[merkel] storage: Supabase`.

### If both databases are connected

Neon wins by default. Set **`STORAGE_BACKEND`** to pin one explicitly:

| Value | Effect |
| ----- | ------ |
| `neon` | Neon only |
| `supabase` | Supabase only |
| `redis` | Vercel KV / Upstash only |
| `file` | Local files (development) |
| blank or `auto` | The default order above |

One gotcha worth knowing: Supabase's integration also injects `POSTGRES_URL`. That is
a Supabase host, and Neon's HTTP driver only speaks to Neon hosts, so the app checks
the hostname and skips Neon rather than failing every query. If you see
`a Postgres connection string is set but its host is not Neon` in the logs, that is
this check working; add the Supabase keys (or `STORAGE_BACKEND=supabase`).

## Step 5: Send enquiries and chat to your inbox (Resend)

1. Sign up at <https://resend.com> (free tier: 3,000 emails a month).
2. **API Keys, Create API Key**, and copy it.
3. In Vercel, add:

   | Name | Value |
   | ---- | ----- |
   | `RESEND_API_KEY` | the key you copied |
   | `FORM_TO` | where enquiries land (comma-separate for several) |
   | `FORM_FROM` | `Merkel Website <onboarding@resend.dev>` to start |

4. **Redeploy.**

You now get an email for every contact-form enquiry and every live-chat message.
Enquiry emails set `reply_to` to the sender, so hitting reply answers the client
directly. Set `CHAT_NOTIFY=off` to keep enquiry emails but stop chat emails.

For production, verify your domain in Resend (**Domains, Add Domain**, then add the
DNS records) and change `FORM_FROM` to something like
`Merkel Website <studio@yourdomain.com>`. Mail from a verified domain is far less
likely to be treated as spam.

## Step 6: Receive mail on your domain and forward it

This gives you `studio@yourdomain.com` that lands in whatever inbox you actually read.
The endpoint is `POST /api/inbound/resend`.

1. In Resend, verify your domain if you have not already, and enable **inbound email**
   for the address you want (for example `studio@yourdomain.com`), following Resend's
   DNS instructions.
2. Create a **webhook** pointing at:

   ```
   https://<your-app>.vercel.app/api/inbound/resend
   ```

   subscribed to the inbound/received email event.
3. Copy the webhook's **signing secret** (it starts with `whsec_`).
4. In Vercel, add:

   | Name | Value |
   | ---- | ----- |
   | `RESEND_WEBHOOK_SECRET` | the `whsec_...` signing secret |
   | `MAILBOX_ADDRESS` | `studio@yourdomain.com` |
   | `FORWARD_TO` | your real inbox |

5. **Redeploy**, then send a test message to `MAILBOX_ADDRESS`.

What happens on each delivery:

- The signature is verified (HMAC-SHA256 over `id.timestamp.body`). Anything
  unsigned, tampered with, or older than five minutes is rejected with `401`.
- The message is archived in the `inbound_emails` table.
- It is forwarded to `FORWARD_TO` with a `Fwd:` subject and `reply_to` set to the
  original sender, so replying goes straight back to them.
- Non-inbound events (delivery receipts and similar) are acknowledged and ignored,
  as is mail addressed to anything other than `MAILBOX_ADDRESS`.

This endpoint is exempt from rate limiting, since it is authenticated by signature.

If inbound email is not available on your Resend plan, set a forwarding rule at your
domain or email provider instead. The endpoint stays closed until
`RESEND_WEBHOOK_SECRET` is set, so leaving it unconfigured is safe.

## Step 7: Optional, send to a desk provider as well

Set `NOTIFY_WEBHOOK_URL` to any endpoint that accepts a JSON `POST`:

```json
{
  "subject": "New enquiry from Ines Hart",
  "text": "Name: ...\nEmail: ...\n\nmessage body",
  "content": "same as text",
  "data": { "id": "...", "name": "...", "email": "...", "message": "..." }
}
```

- **Slack:** create an Incoming Webhook. Slack renders `text`.
- **Discord:** use a channel webhook. Discord renders `content`.
- **Zapier / Make / a help desk:** map `data` onto a ticket.

Email and webhook are independent; configure either or both.

## Step 8: Test it

On your live URL:

1. `/` loads and the hero rotates through your images.
2. `/projects` lists your projects; open one for the full page.
3. `/careers` lists roles; `/contact` shows the form.
4. Submit the contact form. You get the success message and an email.
5. Open the chat, send a message. You get a reply and a notification.
6. Reload and reopen the chat. The conversation is still there, which is what proves
   Step 4 is working.
7. Email `MAILBOX_ADDRESS` and confirm it arrives at `FORWARD_TO`.
8. Visit `/nope` and confirm the styled 404.

From a terminal:

```bash
curl -s https://<your-app>.vercel.app/api/health
# an unsigned webhook must be refused
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  https://<your-app>.vercel.app/api/inbound/resend -d '{}'   # expect 401
```

In the Neon Console, **Tables** shows rows arriving in `enquiries`, `chat_messages`
and `inbound_emails`.

## Local development

```bash
npm install
cp .env.example .env
npm run build
npm start          # http://localhost:3000
npm run dev        # build + auto-restart
```

With nothing configured, the app writes to `./data/` (git-ignored) and skips
notifications, so you can work entirely offline. To test notifications locally, point
`NOTIFY_WEBHOOK_URL` at a <https://webhook.site> URL.

## Environment variable reference

| Variable | Required | Purpose |
| -------- | -------- | ------- |
| `DATABASE_URL` | for Neon | Neon connection string; server side only |
| `STORAGE_BACKEND` | no | Pin one backend: `neon`, `supabase`, `redis` or `file` |
| `SUPABASE_URL` | Supabase alternative | Project URL (`VITE_SUPABASE_URL` accepted) |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase alternative | Server-side key; never expose to a browser |
| `KV_REST_API_URL` / `KV_REST_API_TOKEN` | Redis alternative | Vercel KV credentials |
| `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` | Redis alternative | Upstash credentials |
| `RESEND_API_KEY` | for email | Resend API key |
| `FORM_TO` | for email | Where enquiries and chat land |
| `FORM_FROM` | for email | Verified sender identity |
| `CHAT_NOTIFY` | no | `off` stops chat notifications (default `on`) |
| `RESEND_WEBHOOK_SECRET` | for inbound | Webhook signing secret; endpoint is closed without it |
| `MAILBOX_ADDRESS` | for inbound | The address that receives mail |
| `FORWARD_TO` | for inbound | Where received mail is forwarded (falls back to `FORM_TO`) |
| `NOTIFY_WEBHOOK_URL` | no | Slack / Discord / desk webhook |
| `DATA_DIR` | no | Override local file storage path |
| `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX` | no | API rate limiting (default 60000 / 30) |
| `PORT` | no | Local port (default 3000) |

Legacy aliases `CONTACT_NOTIFY_EMAIL` and `NOTIFY_FROM` still work if `FORM_TO` and
`FORM_FROM` are unset.

## Troubleshooting

**Chat history disappears on reload in production.** No database is connected. Recheck
Step 4, that the variables exist in the **Production** environment, and that you
redeployed afterwards.

**Database writes fail.** Check the function logs. On Neon, a missing table means
`db/schema.sql` has not been run; an authentication error usually means
`DATABASE_URL` was copied from the wrong branch or has been rotated. On Supabase, a
401 or 42501 means you are using the anon key rather than `service_role`.

**No emails arriving.** Check the function logs for `notify email failed`. Usual causes
are a missing `FORM_TO`, or a `FORM_FROM` on a domain not verified in Resend.

**Inbound webhook returns 401.** The log line says why:
`missing_signature_headers` (not a signed request), `signature_mismatch` (wrong
`RESEND_WEBHOOK_SECRET`), or `timestamp_out_of_tolerance` (a replay, or clock skew).

**The contact form still succeeds when email or the database fails.** Deliberate:
persistence and notification are best effort and never block a visitor. The logs show
what failed.

**Rate limiting feels inconsistent.** The limiter is in-memory, so each serverless
instance counts separately. It is a speed bump, not a hard quota. The inbound webhook
is exempt.
